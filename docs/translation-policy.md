# 中文全文翻译与审阅标准

## 完成定义

合格译文让数据库内核、查询处理和存储系统读者能够沿原论文结构完整阅读，不依赖整页截图、临时审校笔记或另行打开 PDF 才能补齐正文内容。准确性和完整性优先于文风润色。

## 进入条件

- 仅使用论文目录中的可读 `source.pdf` 作为正文证据。
- PDF 页数不得超过 `config/policy.yaml` 的全文翻译上限，除非其中已有用户明确授权的单篇例外。
- 已有 `reading_status: translated` 时，不无故重译。
- 缺失原文时使用 `unavailable`；页数超限或当前策略不翻译时使用 `skipped`，不猜正文。

## 正文要求

- H1 统一为 `# <paper.yaml 中的正式原文标题>（中文译文）`，避免猜造未获证据支持的中文书名。
- H1 后统一使用 `## 译者说明`，正文固定为：`本文依据同目录的 source.pdf 翻译。章节、图表、公式、算法、代码与参考文献按原文结构保留。`（文件名在 Markdown 中使用代码格式）。译者说明不得承载抽取、审校或 QA 过程记录。

- 保留原文首页可读的作者机构与联系信息、分类信息、摘要、章节、子节、脚注、结论、致谢、附录、收稿/修订记录和逻辑顺序；出版模板中的纯版权样板可不进入阅读正文，但不得静默丢弃承载技术定义、来源链接或时间信息的内容。
- 保留作者的叙述视角和责任归属，不要求逐个译出 `I/we/my/our/us`。中文可以自然省略或共用主语；只要读者仍能判断是谁提出、假设、观察或评价，就不因少一个“我们”判错。避免把大面积作者自述系统性改成“作者／作者团队”的第三人称转述，也不要把局部观察改成无条件的客观事实。原文明示 `the author(s)` 时可译为“本文作者”；相关工作中的第三方作者应有清楚指代。
- 术语采用数据库领域常用译法；重要术语首次出现可保留英文，后文保持一致。多义词按本文定义和实际动作选义；原文有意区分的机制不能因共用一个中文词而混淆，例如事务回退与数据备份、页整合与节点合并。代码标识符仍按原文保留。
- 保留论断强度和适用条件：`similar` 不提升为“相同”，`can/may` 不删成必然结论，`with/when` 不擅自增加“只有／才能”。实验的默认配置、调优范围、禁用功能、数据分布及基线条件与结果一并保留；不能因看似常识而省略定义、解释或限定句。
- 保留条件的组合与层次：`and/or` 不互换，前提之后的例子不能改成与前提并列的充分条件，`usually/expected/tend to` 不能删成保证。方法或优化的适用条件、何时有必要以及额外代价，都是论断的一部分；不能只保留“更快／可并行”等结论。检查实验范围时区分完整基准套件、选定查询和微基准。
- 公式保留语义、编号和引用关系；不能可靠转写时报告证据缺口。
- 参考文献不仅要逐条保留，正文中的引用锚点也要随对应论断完整保留。单篇深门禁会把源文正文出现而译文正文缺失的参考文献编号列为人工复核候选；区间、数组等方括号数字可能产生候选，必须回到 PDF 判断，不能机械补号。
- 正式表格保留编号和数值，优先转为 Markdown；复杂表格可附局部精裁图，但不得用整页截图替代。
- 图、架构图和流程图应精确裁剪，保留坐标轴、图例、标签、箭头和子图边界，并放在对应段落附近。裁图四边保留少量安全留白；译文已单独转写图注时不把原文图注或相邻正文收入位图。图片须在正常正文阅读宽度下保持最小标签可读，低清资源应从 PDF 渲染页重裁而不是放大旧图。正文内同一资源只引用一次。
- 中文图注须作为图片相邻的可见正文，保留原文图注的编号、解释、单位、子图定义和实验条件。`![替代文本](路径)` 的替代文本（alt）不能代替可见图注；alt 可简短描述图片，完整图注在图片前后只写一次。已有可见图注时不重复添加；图注仅嵌在位图中的候选须回源检查，不依据扫描结果猜写正文。
- 原文有编号的 Listing/代码清单必须保留原编号、标题和完整正文，并与对应 fenced code block 相邻。仅保留“清单 N 展示……”、交叉引用或解释性摘要不算完成；原文可见的 `...` 或 `[...]` 省略标记也应原样保留，不自行补全作者省略的代码。
- 其他未编号的 SQL、代码、伪代码和配置也必须完整保留，使用 fenced code block 并保持可读格式；不能用执行过程摘要替代可见正文，也不能把原文代码改写成自拟的简化实现。
- 参考文献按原编号完整恢复为结构化列表，不使用“详见原文”或摘要列表代替。
- 最终阅读路径不得包含 TODO、contact sheet、候选裁图、覆盖索引、返工日志、自检表或“人工确认后通过”等过程残留。
- 完整性检查只认可读者可见的 Markdown。HTML 注释不得用于凑齐章节、中文覆盖、图表、算法、Listing 或参考文献；未闭合的 HTML 注释从起点至文件末尾都视为隐藏内容。代码围栏、缩进代码块和行内代码中的同形字符仍是读者可见的代码，不按注释处理。
- 正式代码围栏必须包含可读的实质性载荷，正式表格必须同时具有表头和数据行且列结构一致。透明、空白、近乎单色、尺寸过小或只改变极少像素的图片不算正式资源。
- 参考文献节必须由标题后的实际编号条目证明，不能把目录或页眉中的同名文字当成正文起点。页码范围、作者名和 URL 中的 PDF 换行断词必须恢复；悬空的数值范围（例如只有起点而无终点）属于确定性错误，不能忽略。

## 可移植公式语法

译文使用仓库定义的 **GitHub-first 可移植子集**：GitHub 正确渲染是硬要求；同时采用主流 Markdown 阅读器普遍支持的分隔符和标准 TeX，以获得自然兼容性，但不为其他平台牺牲数学语义。AI 代理和译者只需遵守以下规则；平台怪癖及诊断细节由工具处理：

- **数学语义最高优先。** 不改动变量、大小写、上下标归属、数值、运算关系、分组和公式编号；无法确认等价性时停止并报告。
- **只用通用分隔符。** 行内公式写成 `$...$`；块公式的两个 `$$` 各自独占一行。不要使用数学代码围栏、`\(...\)`、`\[...\]` 或 GitHub 专有的反引号分隔形式。
- **编号公式不用 `\tag`。** 必须保留原公式编号及正文引用关系，并把编号作为自包含文本附在同一块公式末尾，例如 `\qquad \text{(2.1)}`。不得为了修复显示而删除编号或改变公式主体。
- **让公式成为独立的 Markdown 元素。** 不要把公式放进代码跨度、斜体、链接文字、脚注定义或图片 alt。公式与正文、标点或 Markdown 标记相邻时，按工具诊断添加 ASCII 空格或改写句子；不要自行发明兼容技巧。
- **表格公式不用 ASCII 管道符。** 公式内不写 `|` 或 `\|`；根据原义人工选择绝对值、范数或关系符号。无法判断含义时停止并报告。
- **字面标点只使用受限 `\verb`。** 公式中确需显示字面 `_`、`%` 或 `#` 时，只能分别写成完整形式 `\verb0_0`、`\verb0%0` 或 `\verb0#0`。不要使用 `\char`、`\_`、`\%`、`\#` 及其双重转义变体；平台原因由公式维护文档定义。
- **只写自包含的 TeX，让工具判定兼容性。** 不定义宏、不更改渲染器设置，也不自行使用字符编码、拆词或空节点等兼容技巧。提交前对变更译文运行 `make math-check-files FILES='path/to/translation.md'` 和 `make math-audit-github FILES='path/to/translation.md'`；只有公式 profile 或全库迁移才运行全量 `make math-check`。只有工具明确给出安全候选时，才可显式运行 `make fix-math FILES='path/to/translation.md'`。

静态兼容错误在 `draft` 和 `translated` 状态下都直接失败。活跃 `draft` 还会拒绝包含数学运算符、完整渐近复杂度或下标向量的强确定性代码跨度候选；单变量、字段名等歧义内容仍必须由审阅者回到 PDF 判断，不能把扫描器未报告当作合法证明。规则编号、GitHub 原因、安全修复边界和外部审计步骤见 `docs/portable-math-maintainers.md`；这些检查不替代公式语义审校。VS Code、Obsidian、Typora、GitLab 等阅读器属于 best-effort 兼容对象，不得以它们的限制为由改坏原公式。

## 审校要求

以下要求规定单篇论文一旦进入翻译或审校后的质量标准；适用于新增、变更及已获授权复审的论文，不构成定期或全库历史复审授权，具体范围由 review workflow 和用户当前请求确定。

首次完整审阅采用独立的“源文清单轮 + 逐项对照轮”。源文清单轮先盘点首页信息、所有章节、脚注、公式、表格、图、算法、代码、结论、致谢、附录、收稿记录和参考文献，再核对译文，不从译文目录反推完整性。逐项对照轮检查关键机制、所有显式数字及其单位、指标、基线和实验条件、比较方向、故障边界、否定、限定条件和结论；不能只抽查代表性数字。作者自述按上下文核对观点与责任归属，代词检索只辅助定位，不比较中英文代词数量，也不为自然省略主语创建缺陷清单。后续修复的复核范围按 [审阅工作流](workflows/review.md) 确定。

对于双栏 PDF，确认文本提取顺序；对于图表、脚注及易混字形，查看可读的局部渲染，不能以整页缩略图或资源存在代替核验。否定、关系符号、数字和标识符等会改变论断的细节，要将 PDF 可见字形与文本提取结果交叉核对；两者不一致时重新定位、放大或换提取方式。上下文帮助发现疑点，不能代替字面证据。

对照每个源段落的解释和限定，而不只核对核心结论或数字；实验设置段与性能结论交叉检查。图注还须检查正常显示图片时的渲染正文，不能以 Markdown 源码中搜到文字或 HTML 的 `alt` 属性存在作为可见性证明。

对机制、证明、选型和实验解释段做双向语义对照：从原文检查前提、动作、状态变化、代价与结论是否均有对应；从译文检查因果、量化和评价是否各有来源。不能用“控制流不灵活”等概括替代“完整物化一个输入”等具体约束，也不能把分散段落综合成作者未写出的解释。新增“此时／随后”等连接词须与伪代码中的集合快照、读写和状态更新时点相符；公式或代码正确不代表其解释和适用边界正确。

标为“原文异常”前，也必须完成上述核对。只有原文确实存在的异常才能保留并加必要短注；无法读清时报告证据缺口，不猜测原文漏词，不把自己的误读写成原文矛盾。

字符数和中英文比例用于发现摘要化风险，不能替代逐节核对。摘要化候选的正文词数由仓库锁定版本的 pypdf 确定性抽取；原始计数和比例只用于诊断。所有 Markdown 侧覆盖与结构统计先排除 HTML 注释。Poppler 布局抽取继续辅助 Listing、资源与参考文献扫描，但不同平台的布局差异不得被误当作确定性错误。机械风险信号只保留在校验输出和当前审阅报告中，不进入仓库元数据。

首次完整审阅未完成，或本次修复尚未通过所需复核时，使用 `reading_status: draft`；该状态允许校验器把过程残留和内容缺口报告为 warning。已有可信完整审阅基线的修复按 review workflow 确定复核范围；只读抽查不修改状态。审阅完成后，将状态改为 `translated`，对当前论文重新运行 `make paper-check`，再由仓库级检查和 CI 在同一 Git revision 上复核确定性门禁。低覆盖、数量差、抽取顺序、作者性人称等机械候选始终只是 warning，必须由审阅者回到 PDF 处置；它们不写入永久 waiver，也不构成语义完整性证明。审阅结论和分工留在 PR、提交或任务报告中。
